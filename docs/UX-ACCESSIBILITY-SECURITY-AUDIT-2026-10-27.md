## Architecture inventory

- Single Android application, Kotlin, Jetpack Compose and Material 3. The inspected configuration uses AGP 8.5.2, Kotlin 1.9.24, Compose compiler 1.5.14, Java 17, compile/target SDK 35 and minimum SDK 26.
- `MainActivity` owns login, lock, account switching, navigation and the screen-level Compose state. `ui/screens`, `ui/dialogs`, `ui/components`, `ui/designsystem` and `ui/theme` contain the presentation layer and shared controls.
- `data/api/PanelApi.kt` and `NodeLogStream.kt` use OkHttp for the real panel and node SSE; models and client-side filtering live in `data/model`; `PanelCache` caches data in memory. The server is the final authorization authority.
- `SessionStore` uses encrypted preferences for account state. The manifest disables platform backup and cleartext traffic and declares RTL support. `BackupManager` handles explicit import/export; workers and `PanelWidgetProvider` provide background monitoring, backup and widgets.
- Locale resources are maintained in `values` and `values-fa`; `LocaleHelper` applies an explicit preference without intentionally replacing unrelated configuration. Tests use JUnit, Robolectric, Compose test APIs and MockWebServer when the actual Android toolchain is available.

### Known incomplete interaction areas

- `ShamsiCalendarPickerDialog.kt` retains compact day cells. A seven-column grid cannot simply be enlarged to 48 dp on a narrow dialog without a responsive redesign. Other independently implemented icon actions may still lack explicit descriptions. Check real touch bounds and design non-overlapping alternatives.
- Additional controls and fields in `UserEditorDialog.kt`, `UserDetailsDialog.kt` and other dialog-specific implementations still use compact sizes or fixed heights. Enlarging a subset does not establish WCAG or Android accessibility conformance for the full app. Labels must be associated with editable fields, not merely drawn nearby.
- `PGTabBar` now limits height and requests that the selected tab be brought into view. Nested scrolling, layout under large fonts and pager synchronization still require runtime and device checks.
- Screenshots for the baseline CI run were uploaded, but their artifact download failed in this environment. No screenshot, light/dark/AMOLED appearance, spacing, clipped content or RTL rendering was inspected visually for this working tree.

## Security observations and priorities

These are source-level findings and risk hypotheses, not a penetration test or proof that a backend can be bypassed. No API, RBAC fallback policy, encryption format or server behavior was intentionally changed.

1. **High — authorization state during account changes.** `data/AdminAccess.kt` deliberately treats unknown permissions and scope as allowed. `MainActivity.kt` clears `PanelCache` during an account switch but refreshes `AdminAccess` asynchronously; the previous account's state can remain in the interim, and cancellation/error handling should be reviewed. Confirm server-side enforcement for every operation. Design and test a session-bound loading/unknown state before changing the existing fail-open behavior or breaking older servers.
2. **High — backup confidentiality and integrity.** `utils/BackupManager.kt` includes account tokens in exports by default, including an unencrypted export path that warns the user. Password-protected exports use PBKDF2-HMAC-SHA256 (65,536 iterations) and AES-CBC/PKCS5 without an authentication tag. Encryption alone does not authenticate a modified file. Plan a versioned authenticated format and migration/read compatibility, review the work factor and make the token/unencrypted-export choices explicit. Do not silently invalidate existing backups.
3. **High — secrets on screen.** Global screen protection defaults off; the existing subscription QR uses targeted `SecureContent`. The API-key reveal now requests that protection too, but it has not been device-verified. User details display a subscription URL without the same targeted wrapper, and clipboard/share paths deliberately move secrets out of the app. Review visibility, clipboard exposure and product expectations before changing those flows. A source wrapper is not proof that a separate dialog window is secure.
4. **High — incomplete Android verification.** GitHub CI compiled the sources and attempted unit tests, but the observed run failed and subsequent fixes need confirmation. Device rendering, layout regressions, SSE cancellation races and lint errors remain possible. The stream stubs used here cannot establish real socket or OkHttp behavior.
5. **Medium — incomplete accessibility and responsive coverage.** Several compact controls, fixed-height fields and unlabeled icon actions remain; custom colors and transparent surfaces need rendered contrast checks, not just integer-color calculations.

## Text-size follow-up

- Appearance now has a localized text-size stepper from 80% to 140% in 10% steps, a sample and a reset to the device default. The setting is saved in encrypted UI preferences. Backups add an optional `theme.font_scale_percent`; older backups leave the existing size unchanged, and excluding settings skips it.
- The Compose root uses the device density unchanged at 100%; other values adjust font scaling without changing display density. The existing 27 dialogs, eight dropdown menus and eight bottom sheets were routed through helpers that carry the parent density into their separate window contents without multiplying it a second time. This is source-level implementation, not proof of behavior on Android. System UI, the home-screen widget and generated PDF/card artwork do not use this Compose setting.
- At the text-size checkpoint, new model, preference/backup, Compose control and window-propagation tests had not run locally with JUnit, Robolectric or Android. See the GitHub Actions evidence above for subsequent results. All eleven static checks and `git diff --check` passed after the follow-up; the Kotlin syntax-only check parsed 62 changed/new files. A standalone runner with JUnit stubs passed three model tests; a second harness with simulated Compose window/density APIs passed 24 observations and forwarding checks. Neither harness validates the real Compose runtime. At the text-size checkpoint there were 1,385 string resources per locale and 58 Kotlin test files with 464 `@Test` occurrences; these are inventory counts, not test results.
- Re-running `testDebugUnitTest`, `lintDebug` and `assembleDebug` still stopped before task execution at the Gradle 8.7 download with an SSL handshake error. No SDK, emulator, `adb`, real rendering or Android build was available.
- Verify default, smaller and larger sizes across screens and nested windows, both locales and system font sizes (including 200%), persistence after process recreation, backup restore with and without settings, accessibility focus and clipping, and secure flags on the affected separate windows.

## Login keyboard follow-up

- A user-provided screenshot from an older installed build shows the login form cut off with a blank band above the keyboard. It does not show the current working tree, so it cannot establish whether the newer code resolves the problem.
- The baseline relied on the unspecified soft-input adjustment while the login layout also applied IME padding. The current manifest explicitly requests `adjustResize`, and the edge-to-edge login viewport applies the IME inset once outside its scrollable column. The layout was extracted so synthetic insets and scrolling can be tested without changing authentication or credential handling. An interaction between window panning and IME insets is a possible explanation, not a confirmed diagnosis of the screenshot.
- Added tests for the manifest adjustment mode, simulated keyboard open/close, already-consumed bottom space and reachability of both login modes in a short viewport. They could not be run locally because Gradle download fails and no Android SDK, emulator or device is available. GitHub CI later ran the unit-test task but reported failures elsewhere; the individual outcomes of these tests were not verified. The eleven static checks and syntax-only parsing passed; a four-case harness used the real viewport function with fake Compose layout/inset APIs. This harness does not verify Android window movement, an actual IME or rendering.
- On a real device, test address, username, password and API-key inputs in both regular and expired-session login; verify the viewport ends at the keyboard without an extra blank band, the focused field and submit action stay reachable, and hiding the keyboard restores the layout. Repeat in both locales, on small/landscape windows, with three-button and gesture navigation and a larger font.
